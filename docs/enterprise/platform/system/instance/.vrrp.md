# VRRP

---

The Virtual Router Redundancy Protocol (**VRRP**) is a computer networking protocol that provides for automatic assignment of available Internet Protocol (IP) routers to participating hosts. This increases the availability and reliability of routing paths via automatic default gateway selections on an IP sub network.

In Haltdos, VRRP is used to configure High Availability (HA) between two instances — a MASTER and a BACKUP. If the MASTER fails, the BACKUP automatically takes over the Virtual IP, ensuring uninterrupted traffic flow.

![VRRP](/img/platform/v7/docs/vrrp.png)

### How to Use:

1. Go to **System > Instance > (Select Instance) > Settings > VRRP Settings**
2. Click **Add Cluster Setting**
3. Configure the fields as described below
4. Click **Save Changes**
5. Click **Deploy Configuration** to apply the VRRP configuration to the instance

:::note
VRRP must be configured on **both** the MASTER and BACKUP instances. The `VIRTUAL ROUTER ID` must be identical on both nodes. The `PRIORITY` value must be higher on the MASTER than on the BACKUP.
:::

---

### Description

**NAME**

Users can specify the user-friendly name for the setting.

```
    Accepted values: String

    Default: Blank 
```

**Example:** `ha-cluster-1`, `vrrp-primary`

---

**PRESERVE STATE**

When enabled, the instance retains its current VRRP state (MASTER or BACKUP) across restarts, rather than re-electing based on priority after a reboot.

```
Accepted values : Enable / Disable
Default         : Disable
```

:::note
Enable this on the MASTER node if you want it to reclaim the MASTER role after recovering from a failure, rather than remaining as BACKUP while the other node has taken over.
:::

---

**INSTANCE STATE**

Users can define the state of the instance. it should be either MASTER or BACKUP.

```
    Accepted values: String

    Default: ens160 
```

| State | Role |
|---|---|
| **MASTER** | Actively forwards traffic and owns the Virtual IP. Should have higher PRIORITY value |
| **BACKUP** | Monitors the MASTER. Takes over the Virtual IP if the MASTER becomes unavailable |

:::caution
Only one instance should be set to MASTER for a given `VIRTUAL ROUTER ID`. Setting both nodes to MASTER will cause a split-brain condition.
:::

---

**DATA INTERFACE**

The network interface on this instance that carries production (data plane) traffic. The Virtual IP will be assigned to this interface on the MASTER node.

```
    Accepted values: Select Data Interface

    Default: ens160 
```

**Examples:** `ens160`, `ens192`, `bond0`

---

**HA INTERFACE**

The dedicated network interface used for VRRP heartbeat (hello) messages between the MASTER and BACKUP nodes. Using a separate HA interface from the data interface is recommended to avoid VRRP messages competing with production traffic.

```
    Accepted values: Select HA Interface

    Default: ens160 
```
**Examples:** `ens192`, `ens224`, `eth1`

---

**VIRTUAL ROUTER ID**

A unique numeric identifier for this VRRP group. Both the MASTER and BACKUP instances must have the same Virtual Router ID to recognize each other as part of the same HA pair.

```
    Accepted values: Integer

    Default: ens160 
```
**Example:** `10`, `50`, `100`

:::caution
The Virtual Router ID must be unique per VRRP group on the same network segment. If two separate HA pairs share the same VRID on the same subnet, they will interfere with each other.
:::

---

**PRIORITY**

Determines which instance becomes the MASTER. The instance with the highest priority value wins the MASTER election.

```
Accepted values : Integer (range: 1–254)
Default         : 0
```

**Recommended values:**
- MASTER node: `100`
- BACKUP node: `90`

:::note
If both nodes have equal priority, the instance with the higher IP address on the HA interface becomes MASTER. Always set different priority values to ensure predictable election results.
:::

---


**MONITORING FREQUENCY**

The interval in seconds at which VRRP hello (advertisement) messages are sent from the MASTER to the BACKUP. The BACKUP uses this to detect if the MASTER is still alive.

```
Accepted values : Integer (in seconds, minimum: 1)
Default         : 0
```

**Example:** `1` — the MASTER sends a hello every 1 second. If the BACKUP misses 3 consecutive hellos (3 seconds), it assumes the MASTER is down and takes over.

:::note
Lower values mean faster failover detection but more network overhead. A value of `1` second is standard for most HA deployments.
:::

---

**Enable VMAC**

When enabled, a Virtual MAC address is assigned to the VRRP group. This Virtual MAC is shared between the MASTER and BACKUP and moves with the Virtual IP during failover, preventing ARP cache issues on downstream devices.

```
Accepted values : Enable / Disable
Default         : Disable
```

:::note
Enable VMAC in environments where downstream switches or routers have slow ARP cache refresh rates, which could cause traffic blackholing after a VRRP failover.
:::

---

**ENABLE VMAC BASE**

When enabled, uses the VRRP-standard virtual MAC address format (`00:00:5e:00:01:<VRID>`) as the base for the Virtual MAC. When disabled, a randomly generated MAC is used.

```
Accepted values : Enable / Disable
Default         : Disable
```

---


**Auth Type**

The authentication method used to validate VRRP advertisement messages between nodes. This prevents unauthorized devices from participating in the VRRP election.

```
    Accepted values: PASS / NONE

    Default: PASS 
```

| Option | Behaviour |
|---|---|
| **PASS** | Simple plaintext password authentication — both nodes must use the same password |
| **NONE** | No authentication — use only in trusted, isolated network segments |

---

**Auth Password**

The password used for VRRP authentication when `AUTH TYPE` is set to `PASS`. Must be identical on both the MASTER and BACKUP instances.

```
Accepted values : String (max 8 characters for VRRP PASS authentication)
Default         : Blank
```
**Example:** `vrrpkey1`

:::caution
AUTH PASSWORD must be identical on both nodes. A mismatch will cause VRRP authentication failures and the BACKUP will not recognize MASTER advertisements, potentially causing both nodes to claim MASTER state simultaneously.
:::

---

**Virtual IPs**

The Virtual IP address(es) that will float between the MASTER and BACKUP. These are the IPs that clients and upstream devices use to connect — they always follow the current MASTER.

```
Accepted values : One or more IPv4 addresses, one per line
                  Format: A.B.C.D or A.B.C.D/prefix
Default         : Blank (required)
```

**Examples:**
- `192.168.1.100`
- `10.0.0.50/24`

---

**Peer IPs**

The IP address(es) of the peer instance's HA interface. The current instance sends VRRP hello messages to these IPs to verify the peer is alive.

```
Accepted values : One or more IPv4 addresses, one per line
Default         : Blank (required)
```

**Example:** `192.168.2.102` — the HA interface IP of the peer node

---

**Excluded Virtual IPs**

Virtual IPs that should be excluded from VRRP advertisement messages. Used when a large number of IPs (e.g., 200+) are assigned to the same interface — excluding most of them from adverts reduces advertisement packet size.

```
Accepted values : One or more IPv4 addresses, one per line
Default         : Blank (optional)
```

**Example:** If you have 200 Virtual IPs but only need `10.0.0.1` to be advertised, list the remaining 199 IPs here to exclude them from advertisements.

:::note
All addresses in `VIRTUAL IPS` and `EXCLUDED VIRTUAL IPS` must be of the same address family (all IPv4 or all IPv6). Mixing families is not supported.
:::
