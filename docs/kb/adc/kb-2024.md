# KB: 2024  

### **CORS Error Documentation**  

#### **Overview**  
When working with web applications, you may encounter **CORS (Cross-Origin Resource Sharing)** errors.  
These appear in the **browser console** when the browser blocks a request to an API hosted on another domain.  

This document explains the most common **CORS errors**, their **causes**, **recommended solutions**, and how to **debug them in Chrome DevTools**.  

---

### **Common Causes of CORS Errors**  
- Missing or invalid headers  
  (`Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials`, `Access-Control-Allow-Headers`, `Access-Control-Allow-Methods`)  

- Preflight request issues (`OPTIONS` blocked, redirected, or invalid response)  

- Credentials and wildcard `*` mismatch  

- Invalid origin (`null`, `file://`)  

- Actual network or connectivity problems  

---

### **1. No `Access-Control-Allow-Origin` Header Present**  

**Meaning**  
The server response did not include the `Access-Control-Allow-Origin` header, so the browser blocked the request.  

**Cause**  
- Server is not configured for CORS.  
- The request was redirected or served from an error page without CORS headers.  

**Solution**  
- Add the `Access-Control-Allow-Origin` header on the server.  
- Use either the exact client origin or `*` (only for **non-credential requests**).  

**How to Debug in DevTools**  
1. Open DevTools → **Network** tab.  
2. Click on the failed request.  
3. Check **Response Headers** → confirm if `Access-Control-Allow-Origin` is missing.

### **2. Wildcard `*` Used with Credentials**  

**Meaning**  
You cannot use `*` in `Access-Control-Allow-Origin` when sending cookies, authorization headers, or credentials.  

**Cause**  
- Server responded with `Access-Control-Allow-Origin: *`, but the request included credentials (cookies, Authorization header, etc.).  

**Solution**  
Replace `*` with the **exact origin** (e.g., `https://example.com`).  
Add both headers explicitly:  

```
    Access-Control-Allow-Credentials: true

    Access-Control-Allow-Origin: https://example.com
```

Remember: when using credentials, `*` is **not allowed**.  

**How to Debug in DevTools**  
- Check request headers for `Authorization` or `Cookie`.  
- Inspect server response → confirm if `Access-Control-Allow-Origin: *` is present.  

---

### **3. Request Header Not Allowed**  

**Meaning**  
A custom header was sent, but the server did not list it in `Access-Control-Allow-Headers`.  

**Cause**  
- Server response omitted the custom header in `Access-Control-Allow-Headers`.  

**Solution**  
- On the server: add the missing header name in `Access-Control-Allow-Headers`.  

**How to Debug in DevTools**  
1. In **Network** tab, inspect the **OPTIONS preflight request**.  
2. Check if your header is missing in the allowed headers list.  


---

### **4. Method Not Allowed**  

**Meaning**  
The HTTP method used is not listed in `Access-Control-Allow-Methods`.  

**Cause**  
- Server only allowed `GET` and `POST`, but request used `PUT`, `DELETE`, etc.  

**Solution**  
- Add missing methods in `Access-Control-Allow-Methods`.  

**How to Debug in DevTools**  
1. Inspect **OPTIONS preflight request**.  
2. Compare requested method with allowed methods.  


---

### **5. Preflight Request Issues**  

Preflight checks (`OPTIONS` requests) must succeed before the actual request.  
Common sub-cases are:  

#### **5.1 Preflight Request Did Not Succeed**  

**Meaning**  
OPTIONS request failed before the actual request.  

**Cause**  
- Server does not support OPTIONS.  
- Proxy/CDN/firewall blocked the request.  
- Server returned 4xx/5xx.  

**Solution**  
- Ensure server responds with **200** or **204** for OPTIONS.  
- Include correct CORS headers in that response.  
 

---

#### **5.2 Redirect Not Allowed for Preflight**  

**Meaning**  
OPTIONS request was redirected (e.g., HTTP→HTTPS, login page).  

**Solution**  
- Handle OPTIONS directly without redirects.  


---

#### **5.3 Response Did Not Pass Access Control Check**  

**Meaning**  
Preflight response returned invalid status (401, 403, 404, 500).  

**Solution**  
- Ensure OPTIONS is accepted and responds with **200/204** plus valid headers.  


---

**How to Debug in DevTools (for all preflight issues)**  
1. Inspect the **OPTIONS request** in Network tab.  
2. Check status code (must be 200/204).  
3. Verify no redirects or missing headers.  

---

### **6. Origin `null` Not Allowed**  

**Meaning**  
Request came from an origin identified as `null`.  

**Cause**  
- Running code directly from `file://`.  
- Sandboxed iframe.  

**Solution**  
- Serve files from `http://localhost` or a real server.  
- Avoid allowing `null` unless absolutely required and safe.  

**How to Debug in DevTools**  
- Check console error → confirm origin shows as `null`.  


---

### **7. Network Error (Failed to Fetch)**  

**Meaning**  
The request failed before CORS validation could occur.  

**Cause**  
- Network failure.  
- Server unreachable (DNS, firewall, TLS issue).  
- Misconfigured HTTPS or proxy.  

**Solution**  
- Confirm the server is accessible.  
- Inspect Network tab for status code.  
- Fix network-level issues before debugging CORS.  

**How to Debug in DevTools**  
1. Open **Network** tab → check if the request reached the server.  
2. If missing → issue is networking, not CORS.
